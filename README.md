# ХЭСЭГ A — Category-Partition (гараар)

Тестлэгдэх функц: `POST /transfer { from, to, amount, currency }`

## A1. Сонголтууд ба төлөөлөх утгууд

| # | Сонголт (category) | Төлөөлөх утгууд | Тэмдэглэгээ |
|---|---|---|---|
| 1 | **from данс** | Valid (байгаа, царцаагүй) | — |
| | | Frozen (байгаа ч царцаасан) | `[ERROR]` |
| | | Missing (огт байхгүй) | `[ERROR]` |
| 2 | **to данс** | Valid (байгаа, from-оос өөр) | — |
| | | Missing (огт байхгүй) | `[ERROR]` |
| | | SameAsFrom (from-той ижил) | `[ERROR]` |
| 3 | **amount** | Zero/Negative (≤ 0) | `[ERROR]` |
| | | Normal (0 < amount < үлдэгдэл, лимитэд багтана) | `[property Positive]` |
| | | ExactBalance (яг үлдэгдэлтэй тэнцүү — хязгаарын утга) | `[SINGLE]` `[property Positive]` |
| | | OverBalance (үлдэгдлээс их) | `[ERROR]` |
| | | OverLimit (үлдэгдэлд багтах ч өдрийн лимитээс хэтэрсэн) | `[ERROR]` |
| 4 | **currency** | Same (данстай ижил валют) | — |
| | | Different (хөрвүүлэлт хийгдэнэ) | `[IF Positive]` |
| 5 | **Өдрийн лимитийн ашиглалт** (далд орчны сонголт) | Empty (өдөрт анхны гүйлгээ) | — |
| | | NearlyFull (лимитийн ихэнх нь аль хэдийн зарцуулагдсан) | `[SINGLE]` |
| | | Full (лимит бүрэн дүүрсэн) | `[ERROR]` |

**Далд орчны сонголт яагаад хэрэгтэй вэ:** `amount` ба `үлдэгдэл` хоёрыг мэдээд ч `ERROR_LIMIT` гарах эсэхийг хэлж чадахгүй — өдрийн лимитийн ҮЛДСЭН хэмжээ нь хүсэлтийн биед огт байхгүй, гэхдээ үр дүнг шийддэг далд төлөв. Үүнийг сонголт болгон тусгаснаар "ижил оролттой хоёр хүсэлт өөр хариу өгөх" тохиолдлыг тайлбарлах боломжтой болно.

## A2. Хязгаарлалтууд ба тэдгээрийн үндэслэл

| Тэмдэглэгээ | Хаана | Үндэслэл |
|---|---|---|
| `[ERROR]` | from: Frozen, Missing · to: Missing, SameAsFrom · amount: Zero, OverBalance, OverLimit · лимит: Full | Алдааны утга бүр ГАНЦ тестээр хангалттай: тухайн алдаа гармагц функц буцдаг тул бусад сонголтын утгууд үр дүнд нөлөөлөхгүй. Эдгээрийг бусадтай хослуулах нь зөвхөн error masking үүсгэнэ. |
| `[SINGLE]` | amount: ExactBalance · лимит: NearlyFull | Хоёулаа ХҮЧИНТЭЙ (алдаа биш) ч ховор хязгаарын төлөв. Нэг удаа шалгахад хангалттай, бүх валют/дансны хослолоор үржүүлэх шаардлагагүй. |
| `[IF property]` | currency = Different нь зөвхөн `[property Positive]` (amount > 0) үед утга учиртай | amount ≤ 0 эсвэл данс байхгүй үед ханшийн хөрвүүлэлт хийгдэхгүй тул "Different валют"-ыг тэр мөрүүдэд шалгах нь хоосон. |

### Давуу эрэмбэ (олон алдаа зэрэг гарвал)

Тодорхойлолтод заагаагүй тул дараах эрэмбийг ӨӨРӨӨ тогтоов:

```
from  →  to  →  amount (лимит)  →  currency
```

**Үндэслэл:** байхгүй эсвэл царцаасан данснаас мөнгө ХАСАХ боломжгүй тул бусад шалгалт утгагүй болно; мөн энэ эрэмбэ нь Лаб 5-ын бодит серверийн зан төлөвтэй (оюутан → хичээл → урьдач нөхцөл) нийцэж байна. Бүх давхар нөхцөлийн хүлээгдэх үр дүн, PICT-ийн олон алдаатай мөрийн oracle энэ эрэмбээр тодорхойлогдоно.

## A3. Бүрэн олонлог ба хязгаарлалтын дараах тоо (N → M)

**Бүрэн олонлог (N):**

```
from(3) × to(3) × amount(5) × currency(2) × лимит(3) = 270 хослол
```

**Хязгаарлалтын дараа (M):**

| Хэсэг | Тоо | Тайлбар |
|---|---|---|
| `[ERROR]` утга бүрд 1 тест | 8 | from: 2, to: 2, amount: 3, лимит: 1 |
| `[SINGLE]` утга бүрд 1 тест | 2 | ExactBalance, NearlyFull |
| Үлдсэн хүчинтэй хослолууд | 2 | from Valid × to Valid × amount Normal × currency(2) × лимит Empty |

```
270 → 12
```

# ХЭСЭГ B — PICT (pairwise covering array)

## B1. Браузерын загвар

[`browser.model`](browser.model) — Лекц 6-ын жишээ: `Content(3) × Cookies(3) × Popups(2) × Addons(2) × Attacks(2) × Forgeries(2)`

| Хувилбар | Команд | Мөрийн тоо (толгойгүй) | Файл |
|---|---|---|---|
| Бүрэн олонлог | — | **144** | — |
| 2-way (анхдагч) | `pict browser.model` | **10** | [results/browser-2way.txt](results/browser-2way.txt) |
| 3-way | `pict browser.model /o:3` | **20** | [results/browser-3way.txt](results/browser-3way.txt) |

**Лекц дээр гараар 9 мөрөнд багтаасан бол PICT 10 мөр өгсөн — яагаад?** PICT нь **greedy (шуналт)** алгоритм ашигладаг: мөр бүрийг үүсгэхдээ тухайн агшинд хамгийн олон шинэ хосыг хамрах утгуудыг сонгодог ба сонголтоо дараа нь эргэж оновчилдоггүй. Хамгийн бага covering array олох бодлого нь NP-хүнд тул PICT хурдыг оновчлолоос илүүд үзэж, "хангалттай бага" хариуг секундын дотор гаргадаг. Иймээс 9 мөрийн онолын оптимум байсан ч greedy зам 10 мөрөнд хүрсэн — энэ нь алдаа биш, алгоритмын зохиомжийн шийдэл юм. Хамрах баталгаа нь хэвээр: бүх хос утга дор хаяж нэг мөрөнд орсон байна.

3-way нь 20 мөр буюу 2-way-гээс хоёр дахин их боловч бүрэн олонлогийн (144) ердөө **13.9%** хэвээр байна — t өсөх тусам мөрийн тоо өснө ч комбинаторын тэсрэлтээс хавьгүй удаан.

## B2. Шилжүүлгийн модель — гурван хувилбар

| Модель | Тайлбар | Мөр | happy path мөр | 1 алдаатай | 2 алдаатай | 3 алдаатай |
|---|---|---|---|---|---|---|
| [`transfer-nc.model`](transfer-nc.model) | хязгаарлалтгүй | **13** | 1 | 1 | 8 | 3 |
| [`transfer.model`](transfer.model) | A2-ын IF хязгаарлалттай | **14** | **0** | 10 | 4 | 0 |
| [`transfer-neg.model`](transfer-neg.model) | `~` сөрөг утгатай | **16** | 2 | 14 | 0 | 0 |

(Файлууд: [transfer-nc.txt](results/transfer-nc.txt), [transfer.txt](results/transfer.txt), [transfer-neg.txt](results/transfer-neg.txt))

**Юу ажиглагдав:**

1. **Хязгаарлалтгүй хувилбар error masking-ээр дүүрэн.** 13 мөрийн 11 нь хоёр ба түүнээс дээш алдаа агуулсан (ж: `Missing | SameAsFrom | Zero | Same` — гурван алдаа зэрэг). Миний эрэмбээр ийм мөр зөвхөн `ERROR_NO_FROM`-ыг л шалгана; үлдсэн хоёр алдаа хэзээ ч ажиглагдахгүй тул тэдгээрийг тус мөрөнд оруулсан нь хоосон зардал.

2. **Хязгаарлалт нэмэхэд мөрийн тоо ӨСӨВ (13 → 14).** Энэ нь анх зөрчилтэй санагдсан ч шалтгаан нь тодорхой: `Amount ≠ Normal` байх бүх мөр заавал `From = Valid, To = Valid` байхаар хязгаарлагдсан тул PICT хосуудыг цөөн мөрөнд "шахаж" чадахаа больсон. Хязгаарлалтын зорилго нь мөрийн тоог багасгах биш — **утгагүй хослолыг арилгах** явдал бөгөөд энд 3 алдаатай мөр бүрэн алга болж, 2 алдаатай нь 8-аас 4 болж буурсан.

3. **Хязгаарлалттай хувилбарт happy path мөр ОГТ ГАРААГҮЙ.** `Valid | Valid | Normal | *` хослол нэг ч мөрөнд тохиолдоогүй, учир нь `Normal` утгыг бусад мөрүүд "эзэлсэн". Covering array нь хос хамралтыг баталгаажуулдаг ч ТУХАЙН чухал мөр (happy path) байх баталгаа өгөхгүй — тиймээс happy path-ыг гараар нэмэх шаардлагатай. Энэ бол pairwise аргыг category-partition-оор нөхөх ёстойн тод жишээ.

4. **`~` сөрөг тэмдэглэгээ нь `[ERROR]`-ийн PICT дэх хувилбар.** 16 мөрийн 14 нь яг НЭГ алдаатай, 2 нь цэвэр happy path (Same ба Different валют). Олон алдаатай мөр огт байхгүй тул oracle тодорхой: мөр бүр ямар `ERROR_*` хүлээхийг эргэлзээгүй хэлнэ.

**A2-ын хязгаарлалт `~`-тэй хамт хэрэгтэй хэвээр үү?** Хэсэгчлэн. `~` нь алдаа хоорондын хослолыг аль хэдийн хориглодог тул `IF [From] <> "Valid" THEN [Amount] = "Normal"` төрлийн хязгаарлалт илүүдэл болно. Гэхдээ `[SINGLE]`, `[IF property]` төрлийн дүрмүүд (ж: ExactBalance-ийг зөвхөн нэг удаа, Different валютыг зөвхөн эерэг amount-тай) `~`-ээр илэрхийлэгдэхгүй тул category-partition-ий хязгаарлалтууд хэвээр хэрэгтэй.

| Шалгуур | Category-Partition (гараар, A) | PICT covering array (B) |
|---|---|---|

Практикт: эхлээд гараар сонголт/утга/тэмдэглэгээг гаргаж, дараа нь тэдгээрийг `~` ба IF хязгаарлалт болгон PICT-д өгч, гарсан мөрүүдэд oracle-оо гараар буулгах нь хамгийн үр дүнтэй.

## C. Дүгнэлт

Энэ лаборатори нь кодгүй, зөвхөн дизайны ажил байсан тул хамгийн их бодол шаардсан алхам нь **сонголт бүрийн төлөөлөх утгыг сонгох** явдал байлаа — ялангуяа `amount`-ыг Zero/Normal/ExactBalance/OverBalance/OverLimit гэж тав хуваахдаа ExactBalance нь алдаа биш, харин хязгаарын ХҮЧИНТЭЙ утга гэдгийг ялгах нь чухал байв. Хоёр дахь хүнд алхам нь далд орчны сонголтыг олох байсан: өдрийн лимитийн үлдэгдэл хүсэлтийн биед огт байхгүй атлаа `ERROR_LIMIT` гарах эсэхийг шийддэг тул үүнийг сонголт болгон тусгасан. Код байхгүй тул олон алдааны давуу эрэмбийг тестээр тогтоох боломжгүй байсан бөгөөд үүнийг өөрөө `from → to → amount → currency` гэж тогтоож, 12, 13-р спецификацийн хүлээгдэх үр дүнг түүнээс гаргасан. Бүрэн олонлог 270 хослолоос `[ERROR]`, `[SINGLE]` тэмдэглэгээний ачаар 12 тест болж буурсан нь category-partition-ий гол үр өгөөжийг тоогоор харууллаа. PICT талд хамгийн гэнэтийн үр дүн нь хязгаарлалт нэмэхэд мөрийн тоо 13-аас 14 болж ӨСсөн явдал байв — хязгаарлалт нь хэмнэлт биш, утгагүй хослолыг арилгах зорилготой гэдгийг ойлгуулсан. Түүнээс ч сонирхолтой нь хязгаарлалттай хувилбарт happy path мөр огт гараагүй: pairwise алгоритм хосын хамралтыг баталгаажуулдаг ч "хамгийн чухал мөр"-ийг баталгаажуулдаггүй тул гараар нэмэх шаардлагатай. `~` сөрөг тэмдэглэгээ нь 16 мөрийн 14-ийг яг нэг алдаатай болгож, oracle-ийг эргэлзээгүй тодорхой болгосон нь `[ERROR]` тэмдэглэгээний PICT дэх шууд хувилбар болохыг баталлаа. Браузерын жишээнд PICT 10 мөр өгч лекцийн гарын 9-өөс нэгээр олон байсан нь greedy алгоритмын зохиомжийн үр дагавар бөгөөд хамгийн бага covering array олох нь NP-хүнд бодлого гэдгийг санууллаа. Ажлын явцад PICT-ийн нэг чимээгүй алдаа ч илэрсэн: хязгаарлалтын өмнөх `#` тайлбар мөр бүх хязгаарлалтыг үл тоодог — моделийн гаралтыг нүдээр шалгаагүй бол буруу тоо тайланд орох байсан. Эцэст нь хоёр арга нь өрсөлдөгч биш гэдгийг ойлгов: category-partition нь алдааны семантик ба oracle-ыг, PICT нь хосын хамралтыг хариуцдаг тул бодит төсөлд хоёуланг хослуулах нь зөв.
